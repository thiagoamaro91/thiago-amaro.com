Keep the model out of the money path: notes from a 48-hour Claude Code build

October 2026 · Thiago Amaro, with Hector MoyanoCode and evidence: github.com/thiagoamaro91/negotiation-agent13 minutes of text

At a hackathon where the other teams' bots were allowed to lie to ours, Hector Moyano and I built trading bots that never call a model, ran Claude Code one level above them, and let an eval say no twice. We came first of 18 teams on the game's negotiating score and finished 4th on the game leaderboard at close. This is how the bots made their decisions, how the Claude Code sessions were run, how a change had to earn its way into the live bots, and the mistake I made on Saturday morning.

What was built: at the Claude Community 48-hour hackathon in Madrid (2-4 October 2026), a
team of two, Thiago Amaro and Hector Moyano, built small Python bots that traded and
negotiated in an agent trading-card game played over an HTTP API, against the game's dealers
and the bots of 17 other teams. Lying between bots was allowed. Result: first of 18 teams on
the game's negotiating score; 4th on the game leaderboard at close.

The design rule: the bots never call a model. Every price they offered and every accept or
reject was plain Python checking a structured offer against the team's limit. Chat text from
other bots was never parsed for terms, so it could not change a price or an accept (one
dealer bot read it only to flag offers whose words contradicted their terms). Claude Code
wrote almost all the code, including the bots' chat lines, ahead of time.

Orchestration: Claude Code sessions worked one level above the bots, each started from a
written hand-off briefing (19 are published in the repo). One conductor session at a time
decided which bot ran, with which settings and when. A read-only monitor session relayed the
humans. An analyst session that never held the team key read the logs and proposed changes as
pull requests. A GitHub issue served as a message bus between the two team members' Claude
sessions. 107 pull requests were merged in 48 hours. From Saturday 16:00 no human approved
individual trades; on Sunday, from the plan approval at 11:52 to the close, the conductor ran
with no human gates inside the game.

Improvement loop: candidate settings were tested on offline evals that replay recorded cases
with no network, no key and no model. Each acceptance rule was written before its run. For
the duel search, candidates were confirmed on held-out seeds and had to beat the baseline by
more than 2 standard errors and not be more than 2 standard errors worse against any opponent
type. About 2,100 duel variants and 9,024 broker policies were screened overnight. Record:
1 change shipped (it came from lab simulations), 2 overnight search winners stopped by the
gate.

Author's part: Thiago designed the conductor model, ran the conductor sessions on his side
(each handed off through a written briefing) and owned the strategy; on Friday he built the
first dealer bot and the team dashboard. Hector built the evals and more of the code.

Lesson (the author's view): a deterministic core makes the search for improvements cheap and
repeatable; a model in the decision loop makes it harder and costlier, not impossible. The
same split, a model working above a plain-code layer that holds the limits, fits regulated
systems where money moves.

Caveats: the "no model" claim is about the bots. From Saturday afternoon into the evening,
Claude subagents run by the conductor sessions also placed some offers through tools kept
outside the repo. Some pull requests were merged without a completed review.

The weekend in numbers

The game

Each team started with a set of collectible cards, some cash, and a private number for what every card was worth to that team. Nobody else could see those numbers. Our bots traded over an HTTP API: they haggled with the game's own dealers, went head to head in duels with other teams' bots over price and, in later rounds, delivery day, and traded directly with other teams. Part of the score was for how well those negotiations went. The server moved in ticks, and each team could accept one offer per tick.

Two rules shaped everything. First, only a structured offer that the other side accepted moved anything; the chat message next to it was just words. Second, the words could be anything. Lying was allowed: your agent could say anything, and so could everyone else's. The kit even allowed trying to prompt-inject the game's dealers.

The money path

The first design call was the one everything else rests on: the bots never call a model. Every price they offered, and every yes or no on a deal, came from plain Python checking the offer against our limit. For the dealer bots and the market desk, the limit was our private value for that card. For the duel bot, it was the per-duel limit the game server gave us. Claude Code wrote almost all of that code, but at run time there was no model anywhere between an offer arriving and an accept going out.

Each lever of the game got its own small bot: dealer bots, a duel bot, a market desk for trades with other teams, and a broker that matched other traders' orders and never traded with our own money. Around them sat a few plain mechanisms:

  • Structured terms only. The bots read the structured "give" and "want" of an offer and nothing else. One dealer bot does read the message text, but only to flag offers whose words don't match their structure, which the game rewarded; a flag is a report, never a decision.
  • Pre-written lines. The chat our bots sent lives in the code as fixed lists of lines that Claude Code wrote ahead of time. The bots pick them in rotation. Nothing is generated while the game runs.
  • One accept at a time. The server allowed one accept per team per tick. Locally, the duel bot held a lock the other bots checked before accepting, so duels came first, and a STOP file halted the market desk's sends at the next tick.
  • Restart keepers. Sixteen processes ran on a Mac Mini, each under a keeper that re-read the configuration before every start. Changing a bot meant editing one line and restarting that one bot.
  • Look before you act. Most bots had a read-only mode next to the live one, so a person or a Claude session could see what a bot would do before it did anything.

This is the check itself, as it ran. The whole decision is a match on the structured fields, a lookup of our limit, and one comparison; nothing in it reads the message.

Why go to this trouble? The strongest reason is prompt injection. Because no model sits in the bots' decision path, nothing another team's bot writes can talk ours into a worse deal: the path reads numbers, not sentences. In the vocabulary Simon Willison uses for the design patterns that secure agents against prompt injection, this is the pattern family taken to its limit: his one-line rule is that once an agent has ingested untrusted input, it must be constrained so that the input cannot trigger a consequential action, and our bots simply never ingest it on the path that acts. I can't claim we blocked an attack on the chat side; nobody can prove a negative from logs. What the logs do show, re-run on the published commit: of the 163 duel deals our bots closed over the weekend, none was outside our limit, and of the 13 offers that swapped in a different card mid-thread, our bots accepted none.

The second reason is smaller: the bots don't depend on our Claude account, so a usage cap on that account doesn't stop them. The Sunday briefing says it plainly: "The bots use no model, so queued scripts keep running if tokens run out." The third reason turned out to matter most for how we improved the bots, and it gets its own section below.

One caveat, because it matters for an honest version of this claim. From Saturday afternoon into the evening, the conductor sessions also ran Claude subagents, and some of them placed offers through tools we kept outside the repo. I can't show from the repo that those offers went through the same check, so everything above is a claim about the bots.

The orchestration

Above the bots, the work ran in Claude Code sessions. Every session started from a written briefing: its goal, its authority, its hard rules, the plan and its checkpoints. Nineteen of those briefings are in the repo. When a session ran out of context, it wrote the briefing for the next one, and a fresh session picked up from there and carried on.

Three roles sat outside the diagram:

  • The PR steward reviewed and merged pull requests, with OpenAI's Codex reviewing selected ones read-only on the exact commit.
  • The team bus, Hector's, was a GitHub issue carrying signed messages; a message there is data, never an operator's yes.
  • Hector's overnight orchestrator ran while my side was out of usage, with Codex on review and deploy.

It didn't start this tidy. On Saturday afternoon several sessions on my side were running in parallel, and at 16:00 Hector and I agreed in person to reset to one conductor session at a time. That evening the conductor still ran two or three subagent lanes, and with the PR-steward sessions running alongside, my side's parallel sessions used up the five-hour usage limit on my Claude account. Overnight, Codex took over the review-and-deploy lane, and Hector ran an orchestrator session that worked through seven work packages and merged fourteen pull requests between 01:30 and 04:52.

Sunday's final window was the cleanest part of the weekend. A planner session wrote the final plan from the scoring evidence and stopped. I approved the plan at 11:52. At 11:55 one conductor session started on the Mac Mini and ran until the result was recorded at 15:01. Its rules were strict: one Opus session, no Opus subagents, Haiku only for reading bulk logs, and all bot work queued as scripts. It queued bot runs, edited configuration lines, flagged offers whose text didn't match their structure, and patched one bot live so it could flag them. The bots moved the money. The conductor set parameters, queued runs and flagged.

Two separate hands-off steps, worth keeping apart: from Saturday 16:00 no human approved individual trades, while people still approved plans and limits; from Sunday 11:52 there were no human gates at all inside the game, because the approved plan authorised every in-game move inside the value rules, and anything outside the game stayed with us. I did send two messages through the monitor that afternoon; neither was an approval the conductor was waiting for, because the plan had already authorised that spending. If you think of autonomy as a slider, the way Andrej Karpathy put it in his Software 3.0 talk, those two dates are the two notches we moved it by, each time after the controls below it had held for long enough.

The pull-request flow was fast. We merged 107 pull requests in 48 hours, 99 of them before the game froze on Sunday, with a median of 15 minutes from open to merge for those 99. Speed only means something next to the quality signals, so here they are: the repo has 1,709 test functions across 63 test files, with 34 known failures listed rather than hidden. Review was a Claude steward session checking protected files and tests, with Codex on the riskier changes. Some pull requests were merged without a completed review, and the section on the mistake is about what that cost us.

On the split of the work: Hector authored 63 of those pull requests, I authored 43, and one came from another account. He built the evals and more of the code. My part was the layer above the code: the conductor model, running my side's sessions through written hand-off briefings, and the strategy. On Friday I also built the first dealer bot and the team dashboard.

The improvement loop

Hector built offline evals for all four bot families. They replay recorded cases with no network, no key and no model. Around them sat lab simulators and two overnight searches, all feeding the same cycle:

  1. The live bots log every event.
  2. Cases are extracted per flow. Game chat never enters a trace.
  3. The acceptance rule is written before the run.
  4. Candidates are generated: hill climbing, sweeps, random variants. Overnight that meant about 2,100 duel versions and 9,024 broker policies screened.
  5. Candidates are scored on training seeds, picked on selection seeds, and confirmed on held-out seeds nobody had tuned against.
  6. The gate. For the duel search, a candidate had to beat the current version by more than 2 standard errors on the same held-out sessions, not be more than 2 standard errors worse against any type of opponent, hold up in a last-tick stress test, and pass the bot's own self-test.
  7. Ship it as a settings file through a pull request (a human merges, the Mac Mini pulls, one bot restarts in its allowed window), or stop and keep what's running.

The record from the weekend: one change shipped and two were stopped. Both overnight search winners looked better than what we were running, and neither cleared the rule written before its search started, so neither went live. Every eval family ended with "keep the baseline". The one change that did ship came from the lab simulations, not from the searches, and a reviewer switched off one of its features before it went live, so what shipped was small.

That sounds like a thin result. I think it's the most useful thing we built. An eval that's allowed to say no is the kind people trust, and ours said no twice to results that looked good at seven in the morning.

The lesson I took is about cost, not possibility. The game was random even with deterministic bots: opponents changed and every session played out differently. That's why the gate compares two versions on the same held-out sessions and asks for more than 2 standard errors. A deterministic core makes that comparison cheap and repeatable. The same session gives the same decision, so the difference between two versions comes from the change, and replaying thousands of sessions overnight needs no model call. Put a model inside the decision loop and every replay costs tokens and time, and the model adds its own variation on top of the game's, so you need more sessions to see the same difference. That's harder and costlier, but not impossible.

The weekend, replayed

The shape is the story of the weekend: rank 10 on Friday night from the first dealer bots and the first team sale; a fall to 16th on Saturday midday after a scored test where our broker matched nothing; 4th by Saturday evening after a clean test and a completed album page; and 4th at the Sunday freeze. The dip is the next section.

The mistake

On Friday night I shut down the agent that had been merging pull requests overnight. By Saturday morning eight pull requests were waiting, and we had a scored test at 11:50. We merged all eight in ten minutes, between 09:23 and 09:33. One of them carried a broker defect. At 11:50 the broker matched nothing, and that test scored zero for us. The fix came from my side and was live at 12:05, fifteen minutes later.

What changed afterwards: one merger session only, and for anything touching the bots or the launcher it waited for a Codex review of that exact commit, or an explicit "no Codex needed". It wasn't perfect. That afternoon one dealer-bot pull request merged before its final review and needed a follow-up. The lesson is plain: eight merges in ten minutes before a live test puts all the risk exactly where you can least afford it. A 15-minute median to merge is only safe with a gate that still holds when the clock is tight.

Where a model would belong

The honest limit of this project is that no model ran at run time, so the fair question is where the model would go. Above the gate, proposing. In the sketch, the counterparty's message, which is untrusted text, goes to a model that reads it, proposes a structured offer and writes the reply. The proposal then goes through the same gate the bots used: plain code checks it against our limit and decides. The model never touches the limit and never sends. That buys what a model is good at, reading messy text and writing a persuasive line, without giving it the wallet. It also keeps the improvement loop intact: the gate still replays deterministically, and the model layer gets its own evals, for how well it reads offers, separate from the decision. This is a design sketch, not what we ran.

What this split means in a regulated estate

I've spent 17 years on the mainframe systems that banks and insurers run on, and this split is the change discipline those teams already live by, applied to a model. Every change there has its test criteria and its backout written before the change window opens, and nobody argues with them once the window is open; that is exactly "the acceptance rule is written before the run". So: a deterministic policy layer between any model and anything that moves money or changes a customer record, holding pre-approved limits and reading structured fields only; the model above it, reading, drafting, proposing, writing the code and the tests; people approving the plan and the limits up front instead of every transaction. The model becomes a very fast contributor that still goes through it.

The people

When the clock started on Friday evening, Hector and I set a long research run going and stepped outside to get to know each other while it ran. Back inside, we read what it had found and made our design calls. It isn't how I expected a hackathon to start, and I'd do it again. Most of the room had gone deep on AI, and the people I got to talk to properly all said the fun part is finding your way around the obstacles. That's been my experience too.

What I'd keep

Five rules this weekend earned, each pointing back to the section that paid for it:

  1. Code holds the limit; the model proposes. A comparison in code can't be argued with, and nothing on the path that acts has read the other side's words. (The money path.)
  2. Write the acceptance rule before the run. A result that looks good at seven in the morning can't argue its way in; the rule was there first. (The improvement loop.)
  3. An eval is only worth having if it is allowed to say no. Ours said no twice, and that is the result I trust most. (The improvement loop.)
  4. Sessions start from briefings, not conversations. Goal, authority, hard rules, plan, checkpoints; a fresh session carries on where the last one stopped. (The orchestration.)
  5. One merger and one gate, even when the clock is tight. Eight merges in ten minutes before a scored test is where the risk concentrates. (The mistake.)
